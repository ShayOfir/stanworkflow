01

Coherence & usability, from the user's chair

The package's central bet is that a researcher can hand it a data frame and a Stan file and get the whole checking loop back for free. That bet mostly pays off once you're inside the pipeline — the trouble is getting in.

What works

Strength

The wflow/regimen verbs — prepare(), tune(), fit(), diagnose(), infer(), run(), resume() — read like a sentence and chain with |> the way a tidyverse user already expects. resume() in particular is a mature touch: it inspects which of $paths$prior / $posterior / $inference exist on disk and re-runs only what's missing, which matters for anything that runs long enough to get killed by a cluster scheduler.

Strength

Diagnostics don't just report numbers, they interpret them. diagnose() flags R-hat > 1.01 and ESS < 400 by name; ppc() turns each Bayesian p-value into a plain-English misfit judgement ("model under-dispersed relative to data"); loo_cv() turns Pareto-k counts into a McElreath-cited action list. For a target user who knows the statistics but not always the idiom, this is the package's best idea — it teaches while it runs.

Strength

quick_fit() (skip all checks, fit only) reveals a real use case behind the design: mass-univariate work, e.g. looping the same model over many ROIs. That's exactly the kind of detail that only comes from having actually run this on the dev/TMS_e1p data.

What costs the user

Gap

No entry point. README.md is one line — the package name. There is no vignette. The single most powerful mechanism in the package, the naming-convention auto-fill in get_stan_data() (a Stan variable literally named n_group or group_id or prior_sigma gets populated automatically from a same-named data-frame column), is documented only in code comments and regex. A new user has no way to learn this contract except by reading stanmodels.R line by line.

Gap

Two objects doing one job. wflow and regimen both expose tune(), fit()/fit_posterior(), run() — and regimen wraps a wflow internally, so a user has to learn both surfaces to understand either. My best read is wflow = one interactive model session, regimen = the same thing with disk checkpointing for batch/mass-univariate work — but that distinction isn't stated anywhere for the user to find.

Gap

infer_contrasts()'s option surface is large and unshown. Continuous vs. categorical, descriptive vs. counterfactual, one-way vs. two-way, plain vs. hurdle outcome — every combination is individually documented (see infer.Rd), but no single example walks a user through choosing between them. This is exactly the kind of decision tree a vignette earns its keep on.

Worth a look

Progress narration (e.g. cat(sprintf("Simulating at %s = %s...", ...)) inside .get_yrep_draws()) goes through cat(), not message(). In an interactive session that's fine; in a scripted regimen run it can't be silenced with suppressMessages().

02

Software engineering practice

The architecture is the strongest part of the codebase: a consistent S3 class per concern (stanmodel, priors, sampler_params, wflow, regimen, contrast, outcome_spec, inference, ppc_results, loo_results), generic dispatch throughout, and roxygen coverage on essentially every export. The packaging around that architecture, however, is still at usethis::create_package() defaults in several places that block a real release.

Blocking, before any release

Blocks R CMD check

DESCRIPTION is unfinished template text — Title: What the Package Does (One Line, Title Case), Authors@R: person("First", "Last", ...), and a License: field that is literally the placeholder `use_mit_license()`, `use_gpl3_license()` or friends to pick a license. There is no LICENSE file. None of this is a style nit — an invalid License: field fails R CMD check outright.

Dependency audit

Cross-referencing every pkg::fn() call in R/ against DESCRIPTION's Imports: turns up five problems, from "undeclared" to "not installable from CRAN at all":

PackageUsed forIn Imports:?Issue
rethinking HPDI() in infer.R Yes Not on CRAN (GitHub-only, McElreath's course package) — disqualifies CRAN submission as-is
loo loo(), relative_eff() — the whole of loocv.R No Hard runtime dependency, entirely undeclared
JWileymisc saveRDSfst() / readRDSfst() in wflow.R No Undeclared; CRAN availability unverified — confirm before relying on it for the I/O layer
tibble deframe() in wflow.R No Undeclared direct call
scales percent() in infer.R plot labels No Undeclared direct call
patchwork wrap_plots() in display.ppc_results_grouped() Inconsistent Imported in NAMESPACE but absent from DESCRIPTION — the two files disagree

The rethinking dependency is the one that matters most: it exists only to compute a highest-posterior-density interval, which is a five-line function or a call to coda::HPDinterval() (CRAN-available). Removing it removes the GitHub-only dependency in one move.

Other engineering findings

Gap

Real test coverage is confined to one file. tests/testthat/test-stanmodels.R exercises stanmodel(), priors(), sampler_params(), .parse_stan_data_block(), and fit()'s guard clauses — and the file itself carries a full duplicate copy of every test, once commented out, once active, left over from a refactor. infer.R (the largest and most computationally consequential file), wflow.R, regimen.R, and loocv.R have no tests at all. For a package whose entire value proposition is correct statistical automation, this is the gap a methodological-journal reviewer will hit first.

Gap

Dead code from unmerged edits. .interpret_bayes_pvalue() and .interpret_coverage() are each defined twice, verbatim, in stanmodels.R. .plot_two_way_scenarios() is defined twice in infer.R. Harmless at runtime (the later definition wins silently) but it's exactly what a lint pass or a second reviewer should have caught before merge.

Worth a look

write.wflow()'s tryCatch fallback is unreachable: the error = handler calls stop() before the intended saveRDS() fallback line, so that fallback never runs. Small, but worth a two-line fix.

Worth a look

old/ (legacy scratch scripts) is not listed in .Rbuildignore, while dev/ correctly is — a stray top-level directory that R CMD check will flag as a NOTE. No CI configuration is present, and most existing tests are gated behind skip_if_not(cmdstanr::cmdstan_version() > "0", ...), so coverage silently drops further on any machine without a full CmdStan toolchain — exactly the situation a CI runner would be in without extra setup.

Net read

The architecture would pass a code review at a software shop; the packaging would not pass R CMD check --as-cran today. Both halves are visible in the same files — this isn't a rewrite, it's a punch list.

03

Fit against Gelman et al. (2020), Bayesian Workflow

Gelman et al. describe workflow as an iterative loop across a growing family of candidate models — build, simulate fake data, check computation, fit, diagnose, compare, expand or simplify, repeat. stanworkflow automates the checking-and-comparison machinery of that loop with real fidelity, but the loop itself, iteration across model space, stays outside the package's scope.

Where it matches

Faithful

Prior predictive checking (§2). run_predictive_checks(prior_predictive = TRUE) fits with skip_likelihood = 1 and routes straight into ppc() — a direct implementation, not a paraphrase.

Faithful

Computational diagnostics (§3–4). diagnose() covers the recommended set — R-hat, ESS, divergences, max-treedepth, E-BFMI — plus McElreath's trankplots, with in-code citations to specific sections of both sources.

Faithful

Posterior predictive checking (§5, Gabry et al. 2019). ppc()'s density overlay, marginal-statistic Bayesian p-values, joint mean–sd plot, and interval-coverage calibration reproduce Gabry et al.'s recommended suite point for point.

Faithful

Model comparison (§7). loo_cv() wraps PSIS-LOO with Pareto-k diagnostics and interpretive guidance tied explicitly to Gelman §7 and McElreath §7.5 — including the (correct, and easy to get wrong) instruction to treat high-k points as substantively interesting rather than as outliers to discard.

Where it stops short

Not covered

The workflow is single-model. Gelman et al.'s central move is comparing across a series of models — nothing in wflow or regimen represents a model family as a first-class object, or supports comparing two fits beyond a user manually calling loo::loo_compare() themselves.

Not covered

No simulation-based calibration. The package supports prior-predictive draws but not the full SBC loop (simulate from the prior with known parameters, refit, check rank statistics) that Gelman et al. and Talts et al. (2018) treat as the stronger computational-validity check — ppc()'s density overlay is a weaker substitute for this.

Not covered

No model-expansion/simplification scaffolding. §3's "start simple and expand, or start complex and simplify" pattern has no representation — the package diffs contrasts within one fit, never Stan code or priors across fits.

Underdeveloped

Reporting (§8) is print methods, not a report. inference's print/plot dispatch is a genuine attempt at "presenting results," but there's no vignette or template turning a completed regimen into a reproducible write-up — the Quarto reports under dev/TMS_e1p look like the right instinct, not yet generalized into the package.

Net read

This is a faithful, well-cited automation of the checking and evaluation stages of Bayesian workflow, applied to one model at a time. The exploratory, multi-model, simulation-calibrated core of what makes Gelman et al. call it a "workflow" rather than "a well-checked fit" is the part still to build.

04

Path to a methodological-journal submission

None of the gaps above are conceptual — they're bounded, known work. In rough order:

  1. Packaging hygiene. Real Title, Description, Authors@R (with ORCID), a valid License: + LICENSE file, URL/BugReports. Fix Imports: against the dependency audit above; replace rethinking::HPDI() with a CRAN-safe equivalent. Deduplicate the repeated function definitions; add old/ to .Rbuildignore. Ship a clean R CMD check --as-cran.
  2. Test coverage. Real tests for infer.R, wflow.R, regimen.R, loocv.R — at minimum, numerical-correctness tests for infer_contrasts() against a hand-computed or simulated ground truth, plus small fast-compiling toy Stan models exercising wflow/regimen end to end. Add GitHub Actions CI.
  3. Documentation. A getting-started vignette running the full loop on a toy dataset, and a second vignette specifying the get_stan_data() naming convention as an explicit contract, not an implicit regex. A pkgdown site is expected by every venue below.
  4. Statistical validation. Cross-check infer_contrasts() and loo_cv() against known results — brms/rstanarm's equivalents, or a reproduction of a published analysis — as evidence for referees.
  5. A stated scope. The manuscript needs a direct answer to "why not brms + tidybayes + loo?" My read of the code: raw-Stan flexibility, naming-convention auto-data-building, integrated interpretive diagnostics, and a checkpointed mass-univariate regimen. That's a real niche — it just isn't stated anywhere yet.

Candidate venues

1

Journal of Statistical Software Best fit

JSS reviews the code itself, not just the manuscript, and its audience is methodologists who write software — exactly this package's register. The S3 pipeline design and explicit Gelman/McElreath alignment make a natural JSS paper. Requires every item above as a hard prerequisite: JSS reviewers run R CMD check themselves.

2

Journal of Open Source Software

A short paper (~1,000 words) plus a repo with tests, docs, and an open license, reviewed in the open on GitHub — faster and lighter than JSS. Its core bar, "automated tests," is currently the package's biggest gap, but once that's closed this is a fast, low-friction complement to a JSS submission.

3

The R Journal

More room for a tutorial-style paper built around a worked case study — the TMS motor-threshold data under dev/TMS_e1p is a ready-made example. Good fit if the authors want to lean on applied narrative more than software-engineering framing.

4

Behavior Research Methods (or a Psychonomic journal)

Worth considering only if the audience is specifically cognitive/neuro/psych researchers and the pitch leans on the package's pedagogical, interpretation-forward diagnostics rather than on software engineering. A substantive, not software, journal — needs a "why this matters scientifically" framing rather than a software-paper one.

In one line

The engineering skeleton and the domain expertise are both already there — what's missing is the packaging discipline (dependencies, tests, docs) that turns a working lab tool into something a methodological journal, and a stranger's Stan model, can actually rely on.
